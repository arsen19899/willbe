# CallQA — анализ записей звонков

На входе — аудиофайл (или папка с записями). На выходе — таблица «что было, чего не было»
по вашему чек-листу, метрики диалога и балл качества разговора.

Что умеет:

- распознаёт речь локально (faster-whisper), без отправки записей наружу;
- разделяет оператора и клиента — по каналам стереозаписи или по голосам;
- ищет ключевые слова и фразы с учётом форм русского слова и ошибок распознавания;
- считает перебивания, доли речи, паузы, монологи, темп речи;
- проверяет, предложил ли оператор заданные товары и услуги;
- оценивает качество диалога по весовому чек-листу и выставляет балл;
- при желании подключает языковую модель для смысловых пунктов
  («отработал возражение», «говорил о выгодах», «вежливый тон»);
- выгружает Excel с раскраской, CSV, JSON и стенограмму.

## Установка (Windows)

### Версия Python — важно

Нужен **Python 3.10, 3.11 или 3.12**.

Под **3.13 и 3.14 установка не пройдёт**: у `ctranslate2` (движок распознавания
речи) и `pymorphy3` пока нет готовых сборок для этих версий, pip пытается
собирать их из исходников и падает.

Если у вас 3.13/3.14 — поставьте 3.12 рядом, удалять новую не нужно,
версии прекрасно живут вместе. Два способа:

```bat
py install 3.12
```

(так умеет новый Python Install Manager — он ставится вместе с 3.14),

либо обычный установщик:
https://www.python.org/downloads/release/python-31210/ → «Windows installer (64-bit)»,
при установке отметьте **«Add python.exe to PATH»**.

### Собственно установка

```bat
cd I:\agent\callqa
install.bat
```

`install.bat` — тонкий запускатель, вся логика в `install.py`. Скрипт сам
перебирает интерпретаторы на машине (лаунчер `py`, `PATH`, стандартные папки
установки, реестр), выбирает подходящий 3.10–3.12 — даже если в `PATH`
по умолчанию стоит 3.14 — собирает `.venv`, ставит зависимости тремя группами
и в конце запускает проверку окружения.

Если подходящей версии не нашлось, скрипт предложит выполнить
`py install 3.12` прямо на месте.

Третья группа (морфология и нечёткий поиск) необязательная: без неё программа
работает, но ищет фразы только дословно.

### Доустановка остального

Базовая установка ставит только необходимое. Всё остальное — одним запуском:

```bat
install_extras.bat
```

Скрипт покажет, чего не хватает, и по каждому пункту спросит:

| Компонент | Что даёт | Как ставится |
|---|---|---|
| **ffmpeg** | чтение mp3, m4a, ogg | скачивается в `bin/` проекта — без прав администратора и правки `PATH` |
| **CUDA-библиотеки** | распознавание на видеокарте, примерно в 10 раз быстрее | cuBLAS и cuDNN кладутся в `bin/`; torch для этого не нужен |
| **локальная модель** | смысловые пункты бесплатно и без интернета | находит запущенную Ollama и настраивает |
| **бесплатный тариф** | то же, но в облаке | Groq, Gemini, OpenRouter, Cerebras на выбор |
| **pyannote** | точное разделение голосов в моно-записях | нужен только для моно; для стерео бесполезен |
| **токен HuggingFace** | pyannote скачивает модель | бесплатный, вводится вручную |

Поставить всё без вопросов: `install_extras.bat --all`
(ключи всё равно придётся ввести — их нельзя получить автоматически).

Только посмотреть состояние: `install_extras.bat --check`

### Если установка не идёт

Посмотреть, какие интерпретаторы скрипт вообще видит:

```bat
python install.py --check
```

Полный лог всех выполненных команд с их выводом — в `install_log.txt`
рядом со скриптом.

Проверить, что всё встало:

```bat
run_cli.bat doctor
```

## Запуск

**Веб-интерфейс** (обычный режим работы):

```bat
run_web.bat
```

Откроется `http://127.0.0.1:8765`. Вкладки: **Анализ** (разбор записей),
**Результаты**, **Обучение** (правила по вашим звонкам), **Настройки**. Перетащите записи в окно или укажите путь к папке.
Кнопка «Показать на примере» покажет готовый отчёт на встроенной стенограмме —
без записей и без скачивания моделей.

**Командная строка** (для пакетной обработки и планировщика):

```bat
run_cli.bat analyze I:\records\2026-08 -o I:\reports
run_cli.bat analyze zvonok.mp3 --model medium --no-llm
run_cli.bat demo
run_cli.bat learn --good D:\records\успешные --bad D:\records\неуспешные
run_cli.bat config --init my_settings.yaml
run_cli.bat doctor
```

из `I:\localmodel`, см. «Где программа берёт Ollama»).

### Ключевые слова и фразы

Пункт чек-листа `type: keyword` — это набор фраз и правило, как их засчитывать:

```yaml
- id: greeting
  title: Поздоровался
  category: 1. Открытие
  type: keyword
  speaker: operator        # в чьей речи искать: operator | client | any
  weight: 8                # вес в итоговом балле
  required: true           # критичный пункт — провал подсвечивается отдельно
  time_to: 40              # искать только в первые 40 секунд
  any_of:                  # достаточно любой из фраз
    - здравствуйте
    - добрый день
```

Дополнительно:

| Поле | Что делает |
|---|---|
| `any_of` | достаточно, чтобы встретилась любая фраза |
| `all_of` | должны встретиться все перечисленные |
| `none_of` | не должно встретиться ни одной |
| `invert: true` | пункт пройден, если фраз **нет** (для запрещённых формулировок) |
| `time_from` / `time_to` | окно поиска в секундах от начала записи |
| `turns_first: N` | искать в первых N репликах говорящего (приветствие, представление) |
| `turns_last: N` | искать в последних N репликах (прощание, следующий шаг) |
| `negation: false` | засчитывать фразу и под отрицанием (по умолчанию «не делаем замер» не засчитывается) |
| `client_first` | клиент сказал это раньше оператора: `warn` — засчитать с жёлтой пометкой, `fail` — не засчитывать |
| `if_client_ended` | трубку бросил клиент, а фразы нет: `na` — не оценивать, `pass` — засчитать |

**Реплики вместо секунд.** Разговор без скрипта не укладывается в секунды:
если клиент сразу заговорил, приветствие звучит на 40-й секунде, и это не
ошибка. Реплика — это ход одной стороны; короткое «угу» собеседника её не
разрывает.

```yaml
- id: greeting
  turns_first: 2                 # в первых двух репликах оператора
  any_of: [здравствуйте, добрый день]

- id: farewell
  turns_last: 2
  if_client_ended: na            # клиент бросил трубку — прощание не оценивается
  any_of: [до свидания, всего доброго]
```

Клиент «бросил трубку», если последним говорил он, оператор после этого не
сказал ни слова, и запись закончилась в пределах двух секунд. Если линия
оставалась открытой, у оператора была возможность попрощаться.

**Отрицание и вопрос.** Поиск понимает, в каком смысле прозвучала фраза:

| Фраза | Как понимается |
|---|---|
| «доставки у нас нет», «монтаж не делаем», «без замера» | отрицание — не засчитывается |
| «нет, доставка есть», «не хотите оформить доставку?», «без проблем доставим» | не отрицание |
| «а доставка есть?», «сколько стоит монтаж» | вопрос |
| «мне монтаж не нужен» (клиент) | отказ клиента |

Правила — по словам и знакам препинания, которые расставляет Whisper, без
языковой модели. Выключить для всего поиска: `matching.negation: false`.

Фраза с префиксом `re:` — регулярное выражение:

```yaml
any_of:
  - "re:\\b\\d[\\d\\s]{2,}\\s*(руб|рубл|тысяч)"
```

**Как ищутся фразы.** Сначала дословно, потом по начальным формам слов
(«предложил бы расширенную гарантию» найдётся по «расширенная гарантия»),
потом — с поправкой на ошибки распознавания. Уровень последнего задаётся
`matching.fuzzy_threshold`: 88 — разумный компромисс, 0 — выключить,
меньше 80 начнут появляться ложные срабатывания.

### Товары и услуги

```yaml
products:
  - name: Расширенная гарантия
    aliases: [расширенная гарантия, продление гарантии, гарантия на два года]
    required: true          # обязателен к предложению в каждом звонке
    group: Допродажа
```

#### Кто завёл речь о товаре

Программа ищет упоминания в речи **обеих** сторон и сравнивает таймкоды.
Товар, о котором клиент спросил сам, продан не благодаря оператору, а вопреки:

| В отчёте | Что произошло | Засчитано |
|---|---|---|
| предложил оператор | оператор назвал первым | да (зелёное) |
| спросил клиент, оператор подхватил | клиент спросил раньше | нет (жёлтое) |
| спросил клиент, оператор не ответил | клиент спросил, оператор так и не назвал | нет (красное) |
| не прозвучало | тема не поднималась | нет |
| клиент отказался сам | клиент первым сказал «монтаж не нужен» | не оценивается (серое) |

Отказ клиента не идёт оператору в минус: позиция выпадает из пункта
«предложил сам» и из доли охвата (`products_declined` — сколько таких).
А «доставки у нас нет» в речи оператора предложением не считается — в
таблице это видно как «только с отрицанием». В листе «Товары» есть
колонка «Как сказал клиент»: спросил, упомянул или отказался.

В таблице видны оба таймкода: `клиент 0:16 → «монтаж» 0:21`.

Строгость задаётся в пункте чек-листа:

```yaml
- id: products_offered
  type: product
  initiative: operator     # operator — только названное первым (по умолчанию)
                           # picked_up — засчитывать и подхваченное
```

#### Группы вместо колонки на каждый артикул

Если позиций больше десятка, `group` — не украшение, а единственный способ
получить осмысленную оценку. Требовать перечислить весь модельный ряд
бессмысленно: в разговоре звучат две-три позиции. Поэтому по каждой группе
считаются свои метрики, и правило пишется по ним:

```yaml
- id: models_named
  title: Назвал минимум две модели
  type: metric
  metric: "products_offered::Модель"
  op: ">="
  value: 2

- id: client_had_to_ask
  title: Клиенту не пришлось спрашивать первым
  type: metric
  metric: products_client_initiated
  op: "<="
  value: 1
```

Доступные метрики (общие и с суффиксом `::Группа`):

| Метрика | Что считает |
|---|---|
| `products_offered` | предложил оператор сам |
| `products_picked_up` | подхватил после вопроса клиента |
| `products_client_initiated` | клиент поднял тему первым |
| `products_missed` | клиент спросил, ответа не было |
| `products_silent` | не прозвучало |
| `products_coverage` | доля обязательных позиций, предложенных оператором |
| `product_initiative_ratio` | доля инициативы оператора среди прозвучавшего |

Эти же числа автоматически становятся признаками при обучении (см. ниже) —
и на практике оказываются одними из самых сильных.

Если включена языковая модель, она дополнительно ловит перефразированные
предложения, которых нет в списке `aliases`, но переписать инициативу не
может: таймкоды сильнее её мнения.

#### Импорт из прайса

Держать большой список позиций руками в YAML — верный способ через месяц
анализировать вчерашний ассортимент.

```bat
run_cli.bat products price.csv --group Модель            :: предпросмотр
run_cli.bat products price.csv --group Модель --apply    :: записать в конфиг
```

Подходит CSV/TSV с колонкой «Название» (плюс необязательные «Группа»,
«Синонимы», «Обязателен») — выгрузка из 1С или сохранённый из Excel прайс.
Кодировка и разделитель определяются сами, cp1251 тоже читается.
Размеры схлопываются: `Модель 3х4`, `3х6`, `3х8` → одна позиция `Модель`
(отключается флагом `--keep-sizes`).

Сохранённую HTML-страницу каталога тоже можно скормить, но это разовый
старт: вёрстка меняется без предупреждения, а главное — в разговоре товар
звучит не так, как на витрине. Полное название с сайта в речи сокращают до
двух слов. Импорт предлагает синонимы черновиком, и **их обязательно нужно
проверить руками**: именно от них зависит, найдётся ли товар в расшифровке.

Импорт ничего не затирает: у существующих позиций сохраняются название,
группа и флаг `required`, добавляются только новые синонимы.

#### Названия, совпадающие с обычными словами

Товары ищутся **и в речи клиента**, поэтому модель по имени «Мария»
поймала бы «меня зовут Мария», а «Весна» — «весной поставим». Для таких
позиций поиск по самому названию выключается, и остаётся вариант с
уточняющим словом:

```yaml
- name: Мария
  aliases: ["re:\\b(?:теплиц|модел|прямостен)\\w*\\s+(?:мария|марию|марии)\\b"]
  match_name: false     # голое «Мария» не искать
```

В настройках это галочка «искать по названию» рядом с товаром.
Автоматически отличить имя модели от обычного слова нельзя — «Гарантия»
тоже односложна, но выключать поиск по ней было бы ошибкой. Поэтому
импорт из прайса не угадывает, а показывает список односложных названий
и предлагает проверить их руками.

#### Готовая база под теплицы

`config/teplicy.yaml` — отраслевой конфиг, собранный по действующим
каталогам chudoteplitsa.ru, gost-teplici.ru, teplitsastore.ru и
teplitsa-rus.ru. Тот же список товаров отдельным файлом —
`config/products_teplicy.yaml`.

| Группа | Что внутри | Позиций |
|---|---|---|
| Тип теплицы | арочная, прямостенная, домиком, каплевидная, Миттлайдер, раздвижная, пристенная, фермерская, навес | 9 |
| Модель | названия из всех четырёх каталогов | 37 |
| Уровень | Люкс / Делюкс / Премиум / Элит — ось допродажи | 4 |
| Комплектация | каркас, поликарбонат, форточки, полив, грядки, фундамент, ленты | 16 |
| Услуги | доставка, сборка в день доставки, гарантия, оплата после сборки, замер | 5 |

Чек-лист построен на групповых метриках: «предложил конкретный тип»,
«назвал минимум две модели», «предложил старшую комплектацию», «сам
предложил услуги», «клиенту не пришлось спрашивать про услуги».

Перед первым разбором стоит потратить пять минут: удалить модели, которыми
вы не торгуете (лишние строки занижают долю предложенного), проверить
синонимы у односложных названий и вписать свои модели в `initial_prompt`.

### Матрица предложений

Плоский список «обязательных товаров» не описывает продажу: фундамент нужен,
когда клиент говорит про болото на участке; старшая комплектация — когда
прозвучала базовая; снятую модель предлагать нельзя вовсе. Для этого —
вкладка **«Предложения»**: каждое правило — условие и что предложить.

| Условие | Когда правило оценивается |
|---|---|
| Всегда | в каждом разговоре |
| Если клиент сказал… | клиент произнёс одну из фраз (под отрицанием — не считается) |
| Если прозвучал товар | товар назвал кто угодно (кроме отказа клиента) |
| Если оператор предложил товар | оператор сам назвал товар-повод |
| Запрещено предлагать | оператор не должен называть выбранное |

Дальше выбирается, что предложить (из списка товаров, с поиском), достаточно
ли одного из выбранного или нужно всё, засчитывать ли ответ на вопрос клиента
и за сколько секунд после повода нужно успеть. Под каждым правилом — оно же
обычной фразой: «Если клиент сказал «болото» → оператор должен сам предложить:
Фундамент из бруса или Грунтозацепы, не позже чем через 180 с».

Как считается:

- правило — отдельный пункт отчёта (колонка «Предложение: …» в своде) со
  своим весом и флагом «критичное»;
- повода не было — «н/д», на балл не влияет;
- предложил заранее, до повода, — засчитывается;
- клиент сам отказался от позиции — «н/д», не в минус;
- опоздал или назвал только после вопроса клиента — не засчитано, в
  обосновании видно почему;
- в «Что исправить» попадает правило с таймкодом повода.

```yaml
offers:
  - id: offer_foundation
    title: Неровный или сырой участок → фундамент или грунтозацепы
    when: client_said               # always | client_said | product_mentioned
                                    # | product_offered | never
    trigger_any_of: [неровный участок, болото, низина]
    offer: [Фундамент из бруса, Грунтозацепы]   # названия ровно как в products
    offer_mode: any                 # any — хотя бы одно, all — все
    credit: operator                # operator — сам; picked_up — и в ответ
    within_sec: 180                 # 0 — до конца разговора
    weight: 6
    required: false
```

В `config/teplicy.yaml` уже есть примеры: участок → фундамент, снег → усиленный
каркас, «бываю на выходных» → автоматика, «Люкс» → старшая комплектация и
выключенный пример запрета. Правила ссылаются на товары по названию: если
переименовать товар, программа предупредит при сохранении.

### Проверки по метрикам

```yaml
- id: no_interruptions
  title: Не перебивал клиента
  type: metric
  metric: operator_interruptions
  op: "=="
  value: 0
```

#### Какое наложение речи — перебивание

По пословным таймкодам программа смотрит, что делал собеседник в момент,
когда оператор заговорил, и что было дальше:

| Тип | Что произошло | Перебивание |
|---|---|---|
| перехватил слово | клиент говорил посреди фразы и замолк вскоре после вступления оператора | да |
| говорил поверх | клиент продолжил говорить, оператор говорил поверх | да |
| одновременный старт | после паузы оба заговорили почти одновременно | нет |
| наложение на конец фразы | клиент договаривал последнее слово предложения | нет |
| вступил в паузу | клиент уже замолчал | не показывается |

Наложение короче `metrics.interruption_overlap_sec` (0.6 с) показывается,
но не считается. Пороги: `interruption_pause_sec` (0.8 с — пауза),
`takeover_stop_sec` (1.5 с — «замолк вскоре»), `simultaneous_start_sec`
(0.4 с — «одновременно»). Все случаи с типом — на листе «Перебивания».

**Когда пункт «н/д».** Если голоса разделены упрощённым способом (pyannote не
сработал), границы реплик приблизительные, и «перебивания» рождаются из
ошибок разметки. Если роли определены неуверенно, «кто первым назвал товар»
теряет смысл. Такие пункты помечаются «н/д», а не проваливаются, и в
замечаниях пишется почему. Роли, опознанные по базе голосов, считаются
надёжными. Отключить: `metrics.na_when_roles_unreliable: false`.

Доступные метрики: `operator_interruptions` (перехват + речь поверх),
`operator_takeovers`, `operator_talkovers`, `client_takeovers`,
`simultaneous_starts`, `client_ended_call`, `client_interruptions`,
`total_interruptions`, `operator_talk_ratio`, `client_talk_ratio`, `long_pauses`,
`longest_pause_sec`, `operator_monologues`, `longest_monologue_sec`,
`operator_wpm`, `client_wpm`, `silence_ratio`, `stop_phrase_hits`,
`profanity_hits`, `response_delay_avg`, `turns`, `duration`.

Операторы сравнения: `<=`, `<`, `>=`, `>`, `==`, `!=`.

### Реакция на реплику (`type: sequence`)

Проверяет не наличие фразы, а связку «повод → реакция». Так без всякой
языковой модели проверяется отработка возражений и ответы на вопросы:

```yaml
- id: objection_handling
  title: Отработал возражение
  type: sequence
  speaker: operator          # кто должен отреагировать
  within_sec: 45             # сколько секунд даётся на реакцию
  if_no_trigger: pass        # возражений не было — пункт не применяется
  trigger_speaker: client
  trigger_any_of: [дорого, я подумаю, у конкурентов дешевле]
  any_of: [понимаю ваши сомнения, зато, давайте посчитаем]
```

`if_no_trigger`: `pass` — нет повода, пункт пройден; `fail` — провален;
`na` — не оценивается и не влияет на балл.

### Счётчик срабатываний (`min_hits`)

Отличает системную работу от разовой обмолвки:

```yaml
- id: politeness
  title: Вежливый тон
  type: keyword
  min_hits: 3                # три вежливых оборота за разговор, а не один
  any_of: [пожалуйста, спасибо, будьте добры, благодарю]
```

### Смысловые проверки

```yaml
- id: objection_handling
  title: Отработал возражение
  type: llm
  weight: 8
  prompt: >
    Клиент высказал сомнение? Если да — оператор попытался его отработать
    аргументами? Если возражений не было — считай пункт пройденным.
```

**Штатный чек-лист их не использует** — он целиком построен на правилах
и работает без всякой модели. Тип `llm` нужен, только если вы хотите, чтобы
пункт понимал формулировки, которых нет в ваших списках. Поле `prompt`
у всех пунктов уже заполнено, достаточно поменять `type` на `llm`.

Модель можно взять локальную (бесплатно) или через API — см. следующий раздел.

Нужен ключ API. Проще всего задать его через `install_extras.bat` — он
проверит ключ и сам пропишет переменную окружения. Вручную:

```bat
setx ANTHROPIC_API_KEY sk-ant-...
```

Без ключа такие пункты помечаются `н/д` и **не портят балл** — остальной
анализ работает полностью. Через `llm.provider: openai` и `llm.base_url`
можно подключить OpenAI-совместимый шлюз, в том числе локальную модель.

#### Локальная модель вместо платного ключа

Программа говорит на протоколе OpenAI, поэтому к ней подключается любой
локальный сервер: Ollama, LM Studio, llama.cpp, Jan, LocalAI.
`install_extras.bat` находит запущенный сервер сам и настраивает подключение.

Вручную:

```yaml
llm:
  enabled: true
  provider: openai
  base_url: http://localhost:11434/v1   # Ollama
  model: qwen3:8b
  api_key: ""        # локальным серверам ключ не нужен
  compact: auto      # укороченный запрос для небольших моделей
```

#### Где программа берёт Ollama

Ollama стоит портативно в `I:\localmodel` (папка «Локальная нейросеть»):
программа — `I:\localmodel\ollama\ollama.exe`, модели — `I:\localmodel\models`,
на диск C: ничего не пишется. CallQA работает с ней так:

- если нейросеть уже запущена (ярлык «Локальная нейросеть» или `start.bat`),
  программа просто к ней подключается;
- если не запущена — `run_web.bat` поднимает `ollama serve` сам при старте,
  с той же папкой моделей и теми же настройками, что и лаунчер нейросети.
  Сервер стартует за секунды и видеопамять не занимает, пока модели не задан
  первый вопрос. Журнал запуска — `data\ollama_serve.log`;
- если сервер упал посреди пачки, программа поднимает его заново и повторяет
  вопрос, а не помечает все оставшиеся звонки «н/д».

Запущенная так Ollama остаётся работать после закрытия CallQA (её же использует
чат нейросети). Остановить — `I:\localmodel\stop.bat`.

```yaml
llm:
  base_url: http://127.0.0.1:11434/v1
  model: qwen3.5:9b
  ollama_exe: 'I:\localmodel\ollama\ollama.exe'  # пусто — искать самому
  ollama_models: ''        # пусто — папка models рядом с портативной установкой
  ollama_autostart: true   # false — только подключаться, не запускать
```

Модель — `qwen3.5:9b`: она есть в наборе нейросети. Прежнюю `qwen3:8b`
установщик `I:\localmodel` удаляет как дубль, поэтому скачивать её обратно
бессмысленно — при следующем `upgrade.bat` она снова пропадёт. Какие модели
есть: `I:\localmodel\ollama.bat list`. Проверить всё сразу: `run_cli.bat doctor` —
строка «Ollama» покажет путь, версию и есть ли нужная модель.

Что поставить (Ollama, `ollama pull <модель>`):

| Модель | Размер | Кому |
|---|---|---|
| `qwen3.5:9b` | 6.6 ГБ | 8 ГБ видеопамяти — лучшее на русском, уже есть в `I:\localmodel` |
| `qwen3:8b` | 5.2 ГБ | 8 ГБ видеопамяти и больше — прежняя модель |
| `qwen3:4b` | 2.6 ГБ | вдвое быстрее, качество чуть ниже |
| `llama3.1:8b` | 4.7 ГБ | альтернатива, хорошо держит диалог |
| `gemma3:4b` | 3.3 ГБ | самая быстрая из пригодных |

`compact: auto` включает для локальных моделей укороченный запрос: только
вердикты «да/нет» по пунктам, без резюме и рекомендаций. Ответ втрое короче —
модель на 8 млрд параметров отвечает за секунды, а не за минуту, и заметно
надёжнее возвращает корректный JSON.

Плата за запросы исчезает полностью, интернет для этой части не нужен.
Расплата — качество: локальная модель на 8 млрд параметров слабее облачной,
на длинных и путаных разговорах будет ошибаться чаще.

#### Видеокарта для распознавания

Для faster-whisper **torch не нужен**: CUDA-библиотеки (cuBLAS, cuDNN)
кладутся рядом с программой отдельно, `install_extras.bat` это делает.
Наличие видеокарты программа спрашивает у ctranslate2 — движка распознавания,
а не у torch, которого при штатной установке нет вовсе.

**«Видеокарта есть» и «на ней можно считать» — разные вещи.** Драйвер
показывает устройство даже без cuBLAS и cuDNN: карта видна, а вычислять
нечем. Программа проверяет и то и другое — пробует загрузить сами
библиотеки, — и если их нет, сразу считает на процессоре вместо того,
чтобы падать на первом файле, и говорит, чего не хватает.

Библиотеки лежат в `bin/` проекта. На Windows этого мало: начиная с
Python 3.8 система не ищет DLL в `PATH`, поэтому папка дополнительно
подключается через `os.add_dll_directory`. Без этого шага файлы лежат на
месте и остаются невидимыми — распознавание падает с «Library
cublas64_12.dll is not found» при том, что файл есть.

В окружении на вкладке «Анализ» видно **фактическое** устройство и тип
вычислений (`cuda/int8_float32`), а не то, что записано в настройках
(`auto/auto`). Разница принципиальная: на GTX 1070 распознавание на
видеокарте идёт примерно со скоростью записи, на процессоре — в несколько
раз дольше самой записи, и по молчаливой полосе прогресса это никак не
отличить от зависания.

Если видеокарта есть, а считает процессор, интерфейс скажет об этом прямо
и подскажет, что делать. Откат на процессор из-за отсутствующих
CUDA-библиотек тоже больше не молчит — он выводится в строке прогресса.

`compute_type` подбирается под карту: `float16` требует архитектуру 7.0 и
новее, на Pascal (GTX 10xx, 6.1) его нет — там `int8_float32`.

#### Скорость локальной модели

Больше всего времени локальная модель тратит не на чтение стенограммы, а на
написание ответа: на GTX 1070 это порядка 20 слов в секунду. Поэтому запрос
к локальной модели устроен экономно:

- модель пишет только список позиций, которые оператор предлагал, и да/нет
  по смысловым пунктам — без цитат и пояснений;
- товары, уже найденные правилами, в вопрос не попадают;
- стенограмма идёт без таймкодов, подряд идущие куски одной стороны склеены.

Для Ollama (адрес на порту 11434) используется её родной протокол:

| Что | Зачем |
|---|---|
| потоковый ответ | `llm.timeout_sec` — ожидание очередного куска, а не всего ответа: пока модель пишет, разбор не обрывается. Предел на весь ответ — вчетверо больше |
| `think: false` | qwen3 не «рассуждает вслух» — это минуты на каждый звонок |
| `format: json` | ответ всегда разбирается |
| `num_ctx` по длине разговора | по умолчанию Ollama берёт 2–4 тыс. токенов и молча отрезает начало длинного звонка |
| `keep_alive: 30m` | модель не выгружается между звонками |

Если модель трижды подряд не уложилась во время, для оставшихся записей
смысловая оценка пропускается, чтобы пачка не превратилась в часы ожидания.
Выключить родной протокол: `llm.ollama_native: false`.

#### Сколько ждать загрузку модели

Два разных ожидания, которые легко перепутать:

| Сообщение | Что происходит | Как часто |
|---|---|---|
| «скачиваю модель…» | загрузка с huggingface.co, до 3 ГБ | один раз на компьютер |
| «готовлю модель…» | чтение с диска и инициализация | один раз за запуск сервера |
| «распознано 4:12 из 10:00» | собственно работа | на каждую запись |

Модель остаётся в памяти: разбор папки из двухсот файлов ждёт загрузку
один раз, остальные записи начинаются сразу. Программа сама говорит,
сколько это заняло: «модель готова за 0:47 — следующие записи начнутся
сразу».

`run_web.bat` поднимает модель **заранее**, пока открывается браузер, — к
моменту, когда запись перетащена, она уже в памяти. Отключается флагом
`--no-preload`, если видеопамять нужна для чего-то ещё.

#### Когда локальный сервер падает

Модель — необязательная надстройка: чек-лист целиком работает на правилах,
и падение сервера не портит разбор. Смысловые пункты помечаются «н/д» и на
балл не влияют — знаменатель считается только по проверенным пунктам.

Программа разбирает типовые поломки и говорит, что делать, вместо того чтобы
показывать кусок лога:

| Что видно в ошибке | Что это | Что делать |
|---|---|---|
| `the provided PTX was compiled with an unsupported toolchain` | сборка сервера собрана более новым CUDA, чем понимает драйвер | обновить драйвер NVIDIA или выключить выгрузку слоёв на GPU |
| `out of memory`, `cudaMalloc` | не хватило видеопамяти | модель поменьше (7–8 млрд, Q4) или меньше слоёв на GPU |
| `process has terminated`, `0xc0000409` | сервер аварийно завершился | то же: драйвер или расчёт на процессоре |
| `model not found` | имя модели в настройках не совпадает с тем, что показывает сервер | исправить `llm.model` |
| `Connection refused` | сервер не запущен | запустить Ollama / LM Studio |
| `timed out` | сервер живой, не успел ответить | увеличить `llm.timeout_sec` |

`install_extras.bat` при сбое видеокарты предлагает обойтись без обновления
драйвера: создаёт вариант модели, считающий на процессоре
(`ollama create qwen3-cpu` с параметром `num_gpu 0`), и сразу его проверяет.
Глобальную переменную вроде `CUDA_VISIBLE_DEVICES` установщик не трогает
намеренно — она отобрала бы видеокарту у распознавания речи, которому та
нужнее: распознавание на GPU идёт в десять раз быстрее, а модель нужна
только для смысловых пунктов.

Первые пять — безнадёжные: сам по себе такой сервер не оживёт. Поэтому после
первой такой ошибки программа перестаёт к нему обращаться до конца разбора.
Иначе пачка из двухсот записей превратилась бы в двести таймаутов по три
минуты — десять часов ожидания вместо получаса работы. Объяснение выводится
один раз, остальные записи разбираются по правилам.

#### Бесплатные облачные тарифы

Если локальную модель ставить не хочется, у ряда провайдеров есть бесплатные
тарифы, и все они говорят на том же протоколе — достаточно поменять две строки
в настройках. `install_extras.bat` предложит их списком и проверит ключ.

| Провайдер | Лимиты бесплатного тарифа | Где ключ |
|---|---|---|
| **Groq** | ~30 запросов/мин, тысячи в сутки | console.groq.com |
| **Google Gemini** | ~1500 запросов в сутки, 10 в минуту | aistudio.google.com/apikey |
| **OpenRouter** | ~50 запросов в сутки на моделях `:free` | openrouter.ai/keys |
| **Cerebras** | ~5 запросов/мин, 1 млн токенов в сутки | cloud.cerebras.ai |

Пример настройки вручную (Groq):

```yaml
llm:
  enabled: true
  provider: openai
  base_url: https://api.groq.com/openai/v1
  model: llama-3.3-70b-versatile
  api_key_env: GROQ_API_KEY
```

Карта не нужна ни одному из них. Лимиты и состав моделей провайдеры меняют —
сверяйтесь на их сайтах.

> **Про приватность.** На бесплатных тарифах стенограмма звонка уходит
> провайдеру, и многие оставляют за собой право использовать её для обучения.
> Для записей с персональными данными клиентов это может быть неприемлемо —
> тогда корректен только локальный вариант или работа вообще без модели.
> Платные тарифы обычно данные для обучения не используют, но это тоже
> стоит проверить в договоре.

Отдельно: лимит суток надо сопоставить с потоком звонков. 50 запросов в сутки
у OpenRouter — это 50 разобранных звонков; у Groq и Gemini запас больше.

#### Где взять ключ и сколько это стоит

**Подписка на Claude (Pro/Max) ключ API не даёт** — это два разных продукта
с раздельной оплатой. Подписка покрывает чат на claude.ai, а ключи выдаёт
консоль разработчика:

1. console.anthropic.com → зарегистрироваться (можно тем же аккаунтом)
2. Billing → пополнить баланс (оплата предоплаченными кредитами)
3. API keys → Create key

## Обучение на своих записях

Вкладка **«Обучение»** (или `run_cli.bat learn`) находит правила по вашим
собственным звонкам. Разложите записи по двум папкам:

```
D:\records\успешные\      — разговоры, закончившиеся так, как надо
D:\records\неуспешные\    — разговоры, закончившиеся плохо
```

Программа расшифрует их, сравнит и предложит пункты чек-листа: фразы,
которые звучат в успешных разговорах заметно чаще, и фразы-маркеры неудачи.
Вы отмечаете, что взять; отмеченное добавляется к чек-листу, **ничего
существующего не перезаписывается**, и всё дальше правится руками
на вкладке «Настройки».

```bat
run_cli.bat learn --good D:\records\успешные --bad D:\records\неуспешные
run_cli.bat learn --good ... --bad ... --apply      сразу добавить в чек-лист
```

Первый прогон расшифровывает записи, повторные берут расшифровки из кэша —
можно свободно крутить строгость отбора, не переслушивая всё заново.

### Как устроен конвейер

Наивный «поиск отличий» между двумя папками выдаёт убедительный мусор.
Поэтому основная работа здесь — не поиск закономерностей, а отсев ложных.
Каждый шаг закрывает конкретный способ обмануться:

| Шаг | Что делает | От чего защищает |
|---|---|---|
| **0. Отложенная выборка** | четверть записей откладывается ДО анализа | оценка «по своим же данным» всегда завышена |
| **0.5 Дубликаты** | записи с одинаковой речью клиента отсеиваются | вторая копия удваивает «подтверждения» фразы |
| **1. Матрица присутствия** | фразы извлекаются один раз, дальше — операции над множествами | позволяет пересчитать отбор сотни раз (шаг 4) |
| **2. Адаптивная поддержка** | порог растёт вместе с корпусом | на 500 записях фраза из трёх — шум |
| **3. Значимость** | точный тест Фишера; при смешивающем факторе — Мантель–Хензель | «на глаз» и «дорого выглядит» — не доказательства |
| **4. Устойчивость** | отбор повторяется на 40 подвыборках | правило, держащееся на двух записях, отсеивается |
| **5. Размер эффекта** | разность долей с доверительным интервалом | «3 из 3» и «30 из 30» — разная уверенность |
| **6. Схлопывание** | окна по одному предложению — одна находка | скрипт оператора не даёт десять правил |
| **7. Комплементарность** | правило берётся, если размечает *другие* записи | один признак не входит в балл дважды |
| **8. Применимость** | правилом может стать только речь оператора до развязки | «клиент сказал “беру”» — не правило качества |
| **8.5 Связки «повод — реакция»** | что оператор делает в ответ на реплику клиента | отдельная фраза без повода — слабое правило |
| **9. Веса** | из логарифма отношения шансов | а не из выдуманного коэффициента |
| **10. Проверка** | итоговый набор правил на отложенных записях | это единственная честная цифра |

Дополнительно: **отрицание** («не буду оформлять гарантию») не засчитывается
как предложение; **формулировка правила** выбирается по редкости слов —
из «подскажите для каких задач вам нужна лампа» правилом станет отличительная
часть «для каких задач», а не общая «вам нужна лампа».

#### Связки «повод — реакция»

Самый полезный тип правила и единственный, который прямо говорит оператору,
что делать. «Давайте посчитаем» — хорошая фраза в ответ на «дорого» и
бессмысленная в начале разговора; отдельно от повода она правилом быть не может.

```yaml
- id: learn_seq_дорого
  type: sequence
  trigger_speaker: client
  trigger_any_of: [дорого, дороговатый]      # повод — однокоренные формы
  any_of: [давайте посчитаем, прослужит пятнадцать лет, что входит в]
  within_sec: 45
  if_no_trigger: pass          # возражения не было — пункт не применяется
```

Три вещи здесь сделаны намеренно:

- **Считается только по записям, где повод был.** Оператор, которому достались
  лёгкие клиенты, не получает штраф за то, чего не происходило. Именно поэтому
  такое правило можно применять ко всем операторам сразу.
- **И повод, и реакция — списки.** Живая речь не повторяет одну фразу дословно:
  клиент говорит «дорого», «дороговато», «дороговато выходит», и по отдельности
  каждая формулировка не набирает статистики. Объединённые — набирают.
- **Список формулировок проверяется на других записях.** Он собирается жадно,
  а жадный отбор на тех же данных находит «правила» и в чистом шуме: из сорока
  фраз всегда найдутся три, случайно легшие в нужную сторону. Поэтому записи с
  поводом делятся надвое: на одной половине список собирается, на другой
  измеряется. Проценты в отчёте — со второй половины.

Списки собраны автоматически и заведомо неполны — прочитайте их и допишите
свои формулировки. Ровно для этого пункт и выводится отдельно, а не
зашивается в балл.

#### Два смешивающих фактора

Обучение проверяет не только длительность разговора, но и **источник записи** —
по имени файла (`ivanov_2026-08-12.mp3` → `ivanov`). Если успешные звонки
собраны у одного оператора, а неуспешные у другого, движок выучит не полезное
поведение, а личные словечки первого. Тогда связь считается внутри слоёв по
источнику, а при полном разделении — обучение прямо говорит, что на таких
данных выводов не будет.

Порядковые номера (`rec12`, `n10`) источником не считаются, а категория из
одной записи не даёт мнимой связи: она «предсказывает» свой исход
безошибочно просто потому, что она одна.

#### Повторы записей

Один разговор, попавший в корпус дважды, — самая незаметная и самая
разрушительная ошибка: статистика считает звонки независимыми, и вторая копия
удваивает «подтверждения» фразы. Ещё хуже, когда запись лежит в обеих папках:
движок ищет отличие между текстом и им же самим.

Повторы ловятся по совпадению окон из пяти слов **в речи клиента** — оператор
работает по скрипту, и по его словам два разных звонка неотличимы. Копия внутри
папки отсеивается (остаётся одна), запись из обеих папок исключается целиком и
попадает в предупреждения: какая метка верна, знаете только вы. Если
«дубликатами» оказалась треть корпуса, это однотипные короткие звонки, а не
копии — тогда обучение ничего не выбрасывает.

### Две цифры в отчёте, и они не равны

**Независимая проверка** — итоговый набор правил на записях, которых движок
не видел ни при отборе, ни при настройке порогов. Это то, чему стоит верить.

**Перекрёстная проверка** — оценка подхода в целом. Она почти всегда выше.
Если разрыв больше 20 процентных пунктов, программа скажет об этом прямо:
значит, была подгонка под конкретные записи.

Обе считаются как *сбалансированная* точность, поэтому перекос 5:1 между
папками не надувает результат — база сравнения всегда 50%.

### Чему здесь не стоит верить

**Смешивающий фактор.** Если успешные разговоры систематически длиннее,
любая фраза «отличает» их — просто потому, что в длинном разговоре успевает
прозвучать больше слов. Программа это измеряет и, если связь умеренная,
считает значимость **внутри слоёв по длительности**. Если длительность
предсказывает исход почти безошибочно, разделить эффекты **невозможно** —
и программа скажет это прямо, а не выдаст красивый список.

**Следствие вместо причины.** Фразы из финала успешных разговоров и вся речь
клиента выносятся в отдельный раздел «правилом быть не может» с объяснением.
«Оформляем заказ» встречается в 100% успешных звонков, но это описание
результата, а не поведения, которому можно научить.

**Размер выборки.** По 5 записей — почти любое совпадение случайно.
Разумный минимум по 20–30 в каждой папке; от 12 включается независимая
проверка.

### Строгость отбора

| Параметр | По умолчанию | Смысл |
|---|---|---|
| минимум записей с фразой | авто | 5% корпуса, но не меньше 3 |
| порог значимости `q` | 0.10 | примерная доля мусора среди отобранного |
| минимальный эффект | 1.6× | во сколько раз чаще должна встречаться фраза |
| минимальная устойчивость | 0.6 | доля подвыборок, где правило подтвердилось |
| контроль длительности | вкл. | считать значимость внутри слоёв по длине |

Ослаблять их можно, но тогда находки — это гипотезы для ручной проверки,
а не готовые правила.

### Как повысить точность обучения

Три рычага, и они делают разное. Ни один не заменяет другие.

**1. Больше размеченных записей — повышает НАДЁЖНОСТЬ.**
Это единственный способ отличить закономерность от совпадения. Обучение
считает точный тест Фишера: при 10 записях в папке разница «7 из 10 против
2 из 10» не проходит порог значимости почти никогда — не потому, что правило
плохое, а потому, что таких данных мало для любого вывода.

| Записей в каждой папке | Что реально получится |
|---|---|
| 5–10 | почти ничего; отдельные находки — совпадения |
| 12–20 | включается проверка на отложенной выборке, первые устойчивые правила |
| 20–30 | появляются связки «повод — реакция»: на них нужны записи с поводом в обеих группах |
| 30–50 | рабочий режим: 5–15 правил, которым можно верить |
| 100+ | видны слабые эффекты и различия между операторами |

Важнее количества — **чистота разметки** и отсутствие повторов: одна запись,
попавшая в корпус дважды, стоит дороже, чем десять недостающих (см. ниже). Двадцать записей, где «успешный»
означает ровно одно (оплата, а не «приятно поговорили»), дают больше, чем сто
разнородных. И длительность: если успешные разговоры систематически длиннее,
обучение это заметит и посчитает значимость внутри слоёв по длине, но лучше
не создавать такого перекоса.

**2. Каталог товаров — повышает ПОКРЫТИЕ.**
Обучение не изобретёт правило про товар, который программа не умеет искать.
Пока модель не описана в `products`, все звонки для неё одинаковы, и
сравнивать нечего. Каталог не улучшает статистику — он даёт статистике то,
что вообще есть с чем сравнивать. Плюс `initial_prompt`: незнакомое название
распознавание уродует до неузнаваемости, и никакой поиск это уже не спасёт.

**3. Разбор инициативы и связок — повышает КАЧЕСТВО признаков.**
Самый недооценённый рычаг. «Товар прозвучал» — слабый признак: он есть и в
успешных, и в провальных звонках. «Клиент спросил про монтаж первым» — сильный,
потому что описывает поведение оператора, а не исход разговора. Метрики
`products_client_initiated` и `products_offered::Группа` попадают в обучение
автоматически и обычно оказываются в верхней части списка находок. Туда же
работают связки «повод — реакция»: «в ответ на “дорого” оператор сказал
что-то из списка» — это поведение, а не исход.

Порядок действий: сначала каталог и `initial_prompt` (это час работы), потом
накопление записей. Наоборот — хуже: сто записей, размеченных до того, как
программа научилась видеть товары, придётся прогонять заново. Расшифровки
кэшируются, так что повторный прогон обучения после правки каталога стоит
секунды, а не часы.

## Оператор и клиент

Кто есть кто, определяется по порядку надёжности:

1. **база голосов операторов** — если у оператора есть образцы голоса;
2. **каналы стерео** — если запись стерео;
3. **признаки речи** — не только «меня зовут» и «компания», которые в живом
   разговоре звучат редко, а то, как говорят стороны: оператор называет цены,
   говорит «у нас есть», «по стандарту», «в подарок», «плюсом к стоимости»;
   клиент обращается «девушка», спрашивает «вы делаете?», «у вас есть?»,
   «это за отдельную плату?» и в целом задаёт заметно больше вопросов;
4. **языковая модель как арбитр** — только когда признаки не дают уверенного
   ответа: модели показывают по 25 реплик каждого голоса, и она отвечает одной
   буквой. Это секунды. Выключить: `speakers.llm_roles: false`.

Часто рядом с клиентом кто-то подсказывает («скажи, что фундамент у нас
есть»). С `speakers.num_speakers: 0`, `min_speakers: 2`, `max_speakers: 3`
pyannote выделяет такой голос отдельно, и он относится к клиенту, а не
перемешивается с оператором.

**Проверка голоса каждой реплики.** Разделение голосов работает кластерами и
на телефонных записях путает короткие ответы: «да, есть двускатная теплица»
оператора попадает в кластер клиента, а один кластер бывает смесью обоих
голосов. Поэтому после назначения ролей у каждой реплики (от 0,8 с) снимается
свой отпечаток голоса и сравнивается с эталонами сторон — средним голосом
оператора и клиента в этом звонке, а если оператор опознан по базе, то и с его
образцами. Реплика переносится к другой стороне, только если заметно ближе к
ней; эталоны уточняются за несколько кругов. Сколько реплик исправлено, видно
в замечаниях к звонку. Правки сохраняются в истории и повторяются при пересчёте
без аудио. Уже разобранные звонки: «История» → «Пересчитать» с отметкой
«сверить голоса заново». Настройки: `voices.refine_segments`, `refine_min_sec`,
`refine_margin` (больше — осторожнее). Нужна нейросетевая модель голоса
(pyannote/wespeaker).

Совет по образцам: образец, вырезанный из того же звонка, даёт сходство около
0,97 и ничего не говорит о точности. Надёжнее 2–3 образца из **разных** звонков.

**Стереозапись** (оператор в одном канале, клиент в другом) — лучший вариант:
разделение точное, перебивания считаются честно. Большинство телефоний
(Asterisk, Mango, Beeline, МТС) умеют писать в стерео — включите эту опцию.
Какой канал чей, задаётся в `speakers.left`; если каналы перепутаны,
программа заметит это по репликам и поменяет их местами сама.

**Моно** — голоса разделяются автоматически. Точный алгоритм (pyannote)
требует бесплатного токена HuggingFace:

1. зарегистрируйтесь на huggingface.co, примите условия моделей
   `pyannote/speaker-diarization-community-1`, `pyannote/speaker-diarization-3.1`,
   `pyannote/segmentation-3.0` и `pyannote/wespeaker-voxceleb-resnet34-LM`;
2. создайте токен в Settings → Access Tokens;
3. впишите его в `speakers.hf_token` (один раз — при вставке поверх старого
   токен задваивается; программа это теперь исправляет сама);
4. установите: `.venv\Scripts\pip install pyannote.audio`

pyannote работает и на процессоре. Чтобы он считал на видеокарте, нужен torch
с CUDA: `install_extras.bat --torch` подберёт сборку сам. Для серии GTX 10
(Pascal) это закреплённая `torch 2.8.0+cu126` — более новые сборки torch эту
серию не поддерживают: ставятся, но видеокарту не видят. Распознавания речи
это не касается — оно работает на видеокарте и без torch.

Для pyannote 4.x основная модель — `speaker-diarization-community-1`; если к ней
нет доступа, программа пробует `3.1`. Загруженная модель держится в памяти
на весь прогон, а не грузится заново на каждый файл. Проверить, что всё
работает: `run_cli.bat doctor` — строка «диаризация» покажет настоящую причину,
если модель не загрузилась.

Без токена работает упрощённый встроенный алгоритм. Он справляется с чистыми
записями, но на шумных путает говорящих — в отчёт добавляется предупреждение
с причиной, почему pyannote не сработал.

### База голосов операторов

Текстовые признаки («меня зовут», «компания») угадывают роли по репликам и
ошибаются на нетипичных разговорах. База голосов решает задачу точно: у
каждого оператора есть образцы голоса, и программа узнаёт его в записи —
**кто оператор, кто клиент и какой именно это оператор**.

Вкладка **«Операторы»** в браузере:

1. **Добавьте оператора**: имя для отчёта и как он записан в именах файлов
   (`Менеджер_Алиса`) — это подсказка на случай, если голос не опознан.
2. **Добавьте образцы голоса** — любым из способов:
   - запись, где говорит только оператор (20–60 секунд речи);
   - канал стерео-записи звонка (левый или правый);
   - **«Разделить голоса»** — загрузите обычный звонок (моно тоже),
     послушайте найденные голоса и нажмите «Это оператор» у нужного.
   2–3 образца из разных звонков надёжнее одного длинного.
3. **Автонабор из папки** — для записей с именем оператора в имени файла.
   Стерео — берётся канал оператора; моно — нужен хотя бы один ручной
   образец, из двух голосов выбирается похожий. Сомнительное пропускается.
4. **«Чей это голос?»** — проверка базы на любой записи: сходство каждого
   голоса со всеми операторами. Удобно, чтобы подобрать порог.

Как это работает при разборе: речь каждого говорящего (канал стерео или голос
после диаризации) превращается в «отпечаток» нейросетью
`pyannote/wespeaker-voxceleb-resnet34-LM` и сравнивается с профилями
операторов. Сходство выше `voices.threshold` (по умолчанию 0.5) — этот голос
получает роль «оператор», остальные — «клиент», имя идёт в отчёт:

- колонка **«Оператор»** в листах «Итог» и «Свод» — `Алиса (голос 0.78)`,
  `Алиса (имя файла)` или `не опознан`;
- лист **«Операторы»** — звонков, средний/мин/макс балл, критичные провалы,
  перебивания и доля речи по каждому оператору;
- предупреждения: каналы перепутаны («дорожки поменяны местами по голосу»),
  оператор опознан неуверенно (двое похожих), имя файла расходится с голосом.

Если голос ниже порога, роли назначаются по репликам, как раньше, а в отчёте
пишется, на кого голос похож больше всего. Без нейросети (нет torch или
модели) работает грубый запасной способ со своим порогом
`voices.threshold_fallback` — отчёт об этом предупреждает.

```yaml
voices:
  enabled: true
  db_dir: operators            # папка базы рядом с программой
  embedding_model: pyannote/wespeaker-voxceleb-resnet34-LM
  threshold: 0.5               # свой голос обычно 0.55–0.85, чужой — ниже 0.35
  threshold_fallback: 0.9
  margin: 0.08                 # отрыв от второго кандидата для уверенного имени
  min_speech_sec: 3.0
  max_speech_sec: 60.0
  override_text_roles: true    # голос важнее текстовых признаков
  use_file_name: true
```

Командная строка:

```bat
run_cli.bat operators add Алиса --alias Менеджер_Алиса
run_cli.bat operators sample Алиса D:\voices\alisa.wav
run_cli.bat operators sample Алиса D:\calls\zvonok.wav --mode left
run_cli.bat operators harvest I:\records\2026-08 --per 5
run_cli.bat operators identify D:\calls\zvonok.mp3
run_cli.bat operators list
run_cli.bat operators rebuild      :: после смены модели отпечатка
```

Сменили `embedding_model` — нажмите «Пересчитать отпечатки голосов»: образцы
хранятся как аудио, отпечатки считаются заново. Папка `operators/` — это
голоса ваших сотрудников: храните и передавайте её так же бережно, как записи.

## История, динамика и пересчёт

Каждый разбор сохраняется в базу `data\callqa.db` (SQLite, один файл, сервер
не нужен). Хранится главное — **расшифровка со словами и таймкодами и разметка
голосов**, то есть всё, на что уходят минуты работы видеокарты. Роли, оператор,
чек-лист, предложения и балл из неё пересчитываются за доли секунды.

Что это даёт:

* **Правки правил — сразу на всём архиве.** Поменяли чек-лист, синонимы товаров
  или матрицу предложений → вкладка «История» → «Пересчитать». Месяц звонков
  пересчитывается за секунды, без повторного распознавания. После сохранения
  настроек программа сама подскажет, сколько звонков посчитаны по старым правилам.
* **Повторный разбор того же файла не распознаёт его заново** — расшифровка
  берётся из истории (узнаётся по содержимому файла, переименование не мешает).
  Сменили модель распознавания — файл будет распознан заново.
* **Динамика.** Средний балл по дням/неделям/месяцам — в целом и по каждому
  оператору, и таблица выполнения пунктов по периодам: сверху самые слабые.
  Дата звонка берётся из имени файла (`2026_08_08_16_14_27_…`), иначе — дата файла.
* **Версии.** У каждого результата записан отпечаток правил, по которым он посчитан;
  прошлые результаты сохраняются (`keep_history`).
* **Кэш языковой модели.** Если вопрос к модели совпал до символа — ответ берётся
  из базы. Пересчёт со смысловой оценкой не гоняет модель по уже заданным вопросам.
* **Образцы голоса добавлены позже.** Отметьте «сверить голоса заново» при
  пересчёте — программа прочитает аудиофайлы (если они на прежнем месте) и
  опознает операторов по новой базе голосов. Без этой отметки оператор берётся
  из прежнего решения.

При первом запуске `run_web.bat` расшифровки из старых отчётов папки `reports`
переносятся в историю сами и сразу считаются по текущим правилам (в консоли
появится строка «История: перенесено…»). Позже то же делает кнопка
«Импорт старых отчётов».

* **Записи, загруженные через браузер**, сохраняются в `data\uploads\<дата>` —
  иначе после добавления образцов голоса их нечем было бы сверить. Разбор по пути
  к папке ничего не копирует. Отключается `storage.keep_uploads: false`.
* **Вкладка «Операторы» → «Опознать операторов в истории заново»** — пересчёт
  всей истории со сверкой голосов по новой базе. Если аудиофайла на месте нет,
  оператор берётся из прежнего разбора; опознание по имени файла пересчитывается
  всегда — новый синоним оператора подхватится без аудио.
* **«Динамика в Excel»** на вкладке «История» — листы «Динамика» (балл по периодам
  и операторам), «Пункты» (выполнение по периодам с цветовой шкалой), «Звонки».
* В разборе звонка — **«История оценок этого звонка»**: как менялся балл от
  пересчёта к пересчёту и по каким правилам.

Командная строка:

```
run_cli.bat history --trends                       последние звонки и динамика
run_cli.bat history --from 2026-08-01 --operator Диана
run_cli.bat rescore                                 пересчитать всё по текущим правилам
run_cli.bat rescore --from 2026-09-01 --llm --report со смысловой оценкой и отчётом Excel
run_cli.bat rescore --voices                        заново сверить голоса с базой операторов
run_cli.bat import-reports                          перенести расшифровки из reports\*.json
run_cli.bat analyze D:\Записи --no-history          разобрать без истории
```

Настройки (`storage` в конфиге):

```yaml
storage:
  enabled: true
  db_path: data/callqa.db     # относительно папки программы
  reuse_transcripts: true     # известный файл не распознаётся повторно
  keep_history: true          # хранить и прошлые результаты пересчётов
  llm_cache: true             # тот же вопрос модели — ответ из кэша
  keep_uploads: true          # загруженные через браузер записи — в data/uploads
  import_old_reports: true    # при первом запуске перенести старые отчёты из reports
```

База — обычный файл: для резервной копии достаточно скопировать `data\callqa.db`
(при закрытой программе). В ней лежат расшифровки разговоров — это те же
персональные данные, что и сами записи.

## Лента событий и свои правила

Разбор звонка теперь устроен в два слоя:

1. **Лента событий** — всё, что произошло в разговоре, одной хронологией: какая
   фраза или товар прозвучали, у кого, на какой секунде и в какой по счёту реплике,
   с каким смыслом (просто упоминание, вопрос или отказ под отрицанием), плюс
   перебивания, паузы и кто завершил разговор. Её видно в разборе звонка —
   раздел «Лента событий», с фильтрами по виду и по говорящему.
2. **Правила — запросы к ленте:** «повод → что должно прозвучать → что нельзя»,
   чья инициатива засчитывается, в каком окне (секунды, первые/последние реплики,
   «не позже N секунд после повода»), когда правило «н/д».

Пункты чек-листа, «обязательные товары» с инициативой и матрица предложений
теперь — частные случаи этой одной модели и считаются одним движком. Настройки
и отчёты остались прежними: на всех сохранённых звонках оценки до и после
перехода совпали до символа. Новое условие больше не требует нового кода —
это новая комбинация полей.

**Вкладка «Правила»** — свои правила, которые не укладываются в чек-лист и матрицу:

| Хочу проверить | Повод | Что должно прозвучать | Нельзя |
|---|---|---|---|
| ответил на «дорого» за 30 с | клиент: «дорого» | оператор: «рассрочка», «скидка»; 30 с, только после повода | — |
| сырой участок → фундамент, сам | клиент: «болото» | оператор: товар «Фундамент»; инициатива — раньше клиента | — |
| спросил, что будут выращивать | — | оператор: «выращивать», смысл — вопросом | — |
| попрощался в конце | — | оператор: «до свидания», в последних 2 репликах | — |
| не говорит «не знаю» | — | — | оператор: «не знаю» |

**«Проверить на истории»** — у каждого своего правила, у каждого пункта
чек-листа и у каждой строки матрицы. Черновик прогоняется по сохранённым звонкам
за секунды, без распознавания и без пересчёта всего разбора: сколько звонков
выполняют условие, и у каких оценка изменится по сравнению с текущей.
Так правку можно проверить до сохранения.

Командная строка:

```
run_cli.bat rules list                    все пункты, строки матрицы и свои правила
run_cli.bat rules test price_objection    прогнать пункт или правило по истории
run_cli.bat rules test bye --from 2026-09-01
run_cli.bat rules events 42               лента событий звонка №42 из истории
```

Свои правила в YAML — раздел `rules` (пример с пояснениями — в конце
`config/teplicy.yaml`).

## Отметки «неверно», самообучение, точечная модель и очередь

### Кнопка «неверно»

В разборе звонка кнопка «неверно» есть у каждого пункта чек-листа (и строк матрицы,
и своих правил), у каждого товара, у оператора, а у каждой реплики расшифровки —
«⇄» (роль перепутана). Исправление:

* **сразу пересчитывает звонок** (без модели — её прежние ответы сохраняются) и
  **остаётся навсегда**: ручное исправление сильнее автоматики и переживает любые
  пересчёты; пункт помечается «вручную», автоматический ответ виден в обосновании;
* отменяется той же кнопкой.

### Самообучение

Вкладка «Обучение» → «Обучение на отметках»:

* **точность пунктов** — сколько отметок, в какую сторону ошибка (засчитал зря /
  не увидел / зря «н/д») и согласно ли правило с отметками сейчас, после правок;
* **подсказки правок**: для «не нашлось, хотя было» — добавить фразу (ту, что вы
  указали в отметке, или общую для таких звонков и не звучащую там, где пункта не
  было); для «засчитано зря» — убрать фразу, из-за которой сработало; для товаров —
  добавить или убрать синоним. **Каждая подсказка проверена до применения**:
  сколько отмеченных ошибок исправит, сколько верных решений сломает и у скольких
  других звонков изменится оценка. Применяется кнопкой — в рабочие настройки;
* **образцы голоса из исправленных реплик**: реплики, которые вы отдали оператору,
  добавляются к его образцам — опознание и проверка голоса по репликам учатся;
* отметки по смысловым пунктам (с комментарием) становятся **примерами для модели**
  в точечных вопросах.

### Точечная модель

`llm.mode: targeted` (по умолчанию для локальной модели): модель получает не весь
разговор, а короткие вопросы там, где правила сомневаются:

| Сомнение | Что видит модель |
|---|---|
| смысловой пункт | разговор (или окно пункта) и примеры из отметок |
| клиент спросил о товаре, оператор по словам не назвал | минута после вопроса клиента |
| у строки матрицы был повод, предложения по словам нет | фрагмент вокруг повода |
| обязательный товар не прозвучал вовсе | только реплики оператора |
| резюме | разговор, сжатый с середины |

Ответ — десяток токенов, поэтому на GTX 1070 вопрос занимает секунды, длинный
разговор не обрезается, а ответ на каждый вопрос кэшируется отдельно: поменяли одно
правило — модель переспросят только о нём. Не больше `llm.max_questions` вопросов
на звонок, важные первыми. `compact` и `full` — прежние режимы одного запроса.

### Очередь

Вкладка «Анализ» → «Очередь»: папка ставится в очередь и разбирается в фоне по
одной записи; очередь хранится в базе и **продолжается после перезапуска**.
Сначала по всей очереди — распознавание и правила (оценки видны сразу), языковая
модель — вторым проходом (`queue.llm_later`). Записи, уже разобранные раньше,
повторно не ставятся. `queue.watch_dirs` — папки, за которыми следить: новые
записи (дописанные больше 30 секунд назад) сами встают в очередь.

```
run_cli.bat queue add D:\Записи\сентябрь     поставить в очередь
run_cli.bat queue list                        что в очереди
run_cli.bat queue run                         обработать всё (и папки слежения) и выйти
run_cli.bat queue clear errors                убрать ошибки из списка
```

`queue run` удобно поставить в Планировщик заданий Windows на ночь.

## Автономность: три уровня

Программа задумана так, чтобы работать «поставил и забыл», без привязок
к аккаунтам и без платы за каждое рабочее место.

**Уровень 1 — только правила. Работает из коробки, стоит ноль.**
Распознавание речи локальное, поиск фраз с морфологией, перебивания, паузы,
доли речи, товары по спискам формулировок, реакция на возражения и вопросы
через `type: sequence`. Штатный чек-лист из 19 пунктов целиком на этом уровне —
никакого интернета, никаких ключей, ничего не уходит наружу. Для большинства
задач контроля качества этого достаточно.

**Уровень 2 — плюс локальная модель. Тоже бесплатно.**
Ollama рядом на той же машине. Добавляет понимание формулировок, которых нет
в ваших списках. Требует видеокарту (или терпение) и разовую загрузку модели.

**Уровень 3 — плюс облачная модель.** Самое высокое качество смысловых
пунктов, но стенограмма уходит наружу. Есть бесплатные тарифы (Groq, Gemini,
OpenRouter, Cerebras) и платные (~1 цент за звонок).

| | Плата | Стенограмма уходит наружу | Нужна видеокарта | Качество смысловых пунктов |
|---|---|---|---|---|
| Только правила | нет | нет | нет | пункты работают по спискам фраз |
| Локальная модель | нет | нет | желательна | хорошее |
| Бесплатный тариф | нет | **да** | нет | хорошее, но есть лимит в сутки |
| Платный API | ~$5–10 за 1000 звонков | да | нет | лучшее |

Переключение — одна строка в настройках, переделывать ничего не нужно.

### Несколько рабочих мест

Программа устроена как веб-приложение, и это решает вопрос без затрат
на каждое место. Поставьте её **один раз** на машину с видеокартой и запустите:

```bat
run_web.bat --host 0.0.0.0 --port 8765 --allow D:\records --allow D:\reports
```

При запуске на внешнем адресе включается **токен доступа**: программа
напечатает готовую ссылку вида `http://адрес:8765/?token=…` — её и отправьте
коллегам. Без токена страница не откроется.

Ключ `--allow` ограничивает, к каким папкам можно обращаться через программу.
Укажите папки с записями и отчётами; без него доступ будет только к домашней
папке. На localhost ни токен, ни ограничение не действуют — там вы у себя.

Остальные открывают присланную ссылку в браузере — устанавливать
им не нужно ничего. Тяжёлое (распознавание и модель) считается на одной машине,
настройки и чек-лист общие для всех, отчёты складываются в одно место.

Если рабочие места изолированы и такой сервер невозможен — папку проекта
можно просто скопировать: она самодостаточна. Модели whisper лежат в кэше
пользователя, чтобы не качать их заново, задайте `asr.download_root`
на папку внутри проекта — тогда переносится вообще всё, вместе с моделью.

## Скорость

Ориентир для часа записей:

| Модель | GPU (RTX 3060+) | GPU (GTX 1070) | CPU (8 ядер) |
|---|---|---|---|
| `small` | ~2 мин | ~4 мин | ~15 мин |
| `medium` | ~4 мин | ~8 мин | ~40 мин |
| `large-v3` | ~7 мин | ~15 мин | ~2 часа |

Для русского телефонного звука `medium` — разумный минимум,
`large-v3` заметно точнее на именах, названиях и числах.
Модель скачивается один раз при первом запуске (`large-v3` ≈ 3 ГБ).

Ускорить: `asr.model: medium`, `asr.vad_filter: true`.

### Тип вычислений и старые видеокарты

`asr.compute_type: auto` подбирает тип по вычислительной способности карты.
Это важно: **на Pascal (серия GTX 10xx) float16 не поддерживается**.
Если задать его вручную, CTranslate2 молча откатится на другой тип и вы
потеряете скорость, ничего об этом не узнав.

| Видеокарта | Способность | Тип |
|---|---|---|
| RTX 20xx и новее | 7.0+ | `float16` |
| GTX 10xx (Pascal) | 6.1 | `int8_float32` |
| Более старые | < 6.1 | `float32` |

`install_extras.bat` определяет это сам и прописывает в настройки.

Для работы на видеокарте нужны cuBLAS и cuDNN — на Windows их нет в pip,
поэтому доустановщик кладёт готовые библиотеки в `bin/` проекта.
**torch для распознавания не нужен вовсе** — faster-whisper работает
на CTranslate2. torch требуется только для pyannote.

## Если что-то не так

| Симптом | Причина и что делать |
|---|---|
| `install.bat` падает на установке пакетов | почти всегда — Python 3.13/3.14. Поставьте 3.12: `py install 3.12` |
| `No runtime installed that matches 3.12` | лаунчер `py` показывает версию, которой на самом деле нет. Выполните `py install 3.12` и повторите |
| Окружение не создалось, дальше всё падает с «не удалось найти указанный путь» | то же самое: `.venv` не собрался. Диагностика — `python install.py --check` |
| В окне установки строки рвутся на середине, `'…' is not recognized` | старая версия `install.bat` с кириллицей — `cmd.exe` её ломает. Возьмите новую (файлы на латинице) |
| «Не удалось прочитать аудио» | нет ffmpeg в `PATH` — см. раздел «Установка» |
| «Не удалось загрузить модель… 403 / connection» | нет доступа к huggingface.co. Скачайте модель на машине с сетью и укажите путь к папке в `asr.model` |
| Роли перепутаны | поправьте `speakers.left`, для моно — подключите pyannote |
| Слишком много перебиваний | поднимите `metrics.interruption_overlap_sec` до 0.8–1.0 |
| Фразы не находятся | посмотрите стенограмму на листе «Транскрипт» — обычно расходится формулировка; добавьте вариант в `any_of` или поднимите `fuzzy_threshold` |
| Ложные срабатывания | опустите `fuzzy_threshold` до 92–95 или задайте 0 |
| Смысловые пункты `н/д` | не задан `ANTHROPIC_API_KEY` |
| Не хватает видеопамяти | `asr.model: medium` или `asr.device: cpu` |

```
callqa/
  config/default.yaml     эталонные настройки: чек-лист, товары, фильтры, пороги

  operators/              база голосов операторов (создаётся сама)
  config/teplicy.yaml     отраслевой конфиг: теплицы, группы товаров, метрики групп
  config/products_teplicy.yaml  та же база товаров отдельным файлом
  callqa/
    audio.py       чтение аудио, стерео/моно, тишина
    asr.py         распознавание речи (faster-whisper)
    diarize.py     разделение по голосам для моно
    roles.py       кто оператор, кто клиент
    voices.py      база голосов операторов и опознание по голосу
    text.py        морфология русского и поиск фраз
    metrics.py     перебивания, паузы, доли речи, монологи

    rules.py       правила как запросы к ленте: чек-лист, товары, матрица, свои правила

    feedback.py    отметки «неверно»: ручные исправления, точность правил
    selflearn.py   подсказки правок по отметкам, образцы голоса, примеры для модели

    jobqueue.py    очередь разборов: фон, два прохода, слежение за папками

    storage.py     история в SQLite: расшифровки, результаты, динамика, кэш модели
    report.py      Excel / CSV / JSON
```

## Приватность

Записи и стенограммы не покидают компьютер: распознавание, поиск фраз
и метрики считаются локально. Наружу уходит только текст стенограммы —
и только если включена смысловая оценка (`llm.enabled: true`).
Выключите её в настройках, если это недопустимо: чек-лист по ключевым фразам,
товары и все метрики продолжат работать.
